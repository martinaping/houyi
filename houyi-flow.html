HOUYI · 企业微信会话存档服务

把企业微信里的聊天记录，
自动备份成可长期保存、可被业务使用的数据

简单说：企业微信本身只提供「会话存档」的拉取接口，houyi 就是一个 7×24 小时运行的搬运工—— 定时把员工与客户之间的消息、图片、语音、文件拉下来，解密、去重、存到对象存储， 再通过消息队列交给下游系统做审计、客服质检或 CRM 分析。

Spring Boot 3.2 Java 21 企业微信 Finance SDK MySQL / H2 Redis 阿里云 OSS RocketMQ / Redis Streams
01

它到底解决什么问题

企业微信的「会话存档」有合规要求：聊天内容必须留痕。但官方只给原始接口，不给存储、不给重试、不给业务推送。houyi 补的就是中间这一整段。

输入

企业微信会话存档

按企业（corpId）拉取增量消息流，每条消息有唯一序号 seq，支持加密传输。

处理

解密 + 下载 + 去重

私钥解密消息体；图片语音文件从企微下载，按 MD5 去重后上传到 OSS。

输出

消息队列里的标准 JSON

文本、媒体地址、会话信息统一成一条条消息推给下游，失败自动延迟重试。

打个比方：企业微信是「发货方」，houyi 是「快递分拣中心」。 Redis 里记着「上次读到第几件包裹」的书签；MySQL 记着企业名单和每件包裹的处理结果； OSS 是仓库；消息队列是通往各个下游业务系统的传送带。

03

主流程：一条消息的完整旅程

下面按代码实际执行顺序走一遍。每一步都附了它在代码里的具体动作，方便对着源码看。

1

启动：先同步企业名单

应用启动时读取 wework-corps.yml，把每个企业的 corpId、secret、私钥、启用状态写入数据库。启用的企业标记为 status=1，停用的标记为 0。私钥既可以直接写在配置里，也可以指定私钥文件路径。

类：CorpConfigService.syncCorpConfigToDatabase()　表：企业配置表
2

给每个启用的企业开一条拉取线程

启动完成后查询所有 status=1 的企业，为每家创建一个独立线程 msg-thread-<corpId>。线程里是死循环：拉一批 → 处理 → 休眠 200ms → 再拉，避免把接口打爆。也可以在运行期通过接口手动触发某个企业。

类：Start.run() / Start.triggerCorpId()　线程名：msg-thread-{corpId}
3

从 Redis 取出「读到哪儿了」

每家企业在 Redis 里有一个书签键 last_seq_<corpId>。服务重启后从上次的 seq 继续拉，不会重复、也不会漏。每次最多拉 500 条，接口超时 100 秒。

调用：Finance.GetChatData(sdk, lastSeq, 500, "", "", 100, slice)　Redis Key：last_seq_{corpId}
4

解密：把密文还原成 JSON

企微返回的是加密消息。先用配置的 RSA 私钥解出随机密钥，再用它解密消息体，得到一条条 JSON。若遇到会话存档过期、IP 不在白名单、token 缺失等错误码，线程会按不同时长休眠后再试（5 / 10 / 30 分钟）。

调用：RSAEncrypt.decryptByPriKey() → Finance.DecryptData()　错误码：301052 / 301042 / 41001
5

分类分流：纯文本直接走，媒体进下载池

文本、撤回、位置、红包、链接这类消息不需要下载文件，直接入库并推送 MQ。图片、语音、视频、表情、文件、混合消息（mixed / chatrecord）则提交到下载线程池，由后台线程慢慢处理，不阻塞拉取主循环。

类：Message.sendMsg() / DownloadThreadKeeper.execute()　线程池：核心 8、最大 100、队列 10000
6

下载媒体文件并校验

根据消息里的 sdkfileid 从企微把文件分片下载到本地临时目录，下载过程中做 MD5 校验，确保文件没有损坏。大文件有单独的超时控制。

类：MsgHandler.downMedia() / MixedHandler　临时目录：/tmp
7

MD5 去重，再上传 OSS

上传前先查 MD5 索引表：同一个文件（比如群聊里多人转发的同一张图）只上传一次，后续直接复用已有的 OSS 地址，省流量也省存储。新文件上传成功后，把 OSS 路径写回原始消息表。

类：MsgHandler → OssUtil.upload()　去重表：md5 索引　回写：原始消息.ossPath
8

组装统一 JSON，推送消息队列

处理完成后组装标准 JSON：原始消息字段 + seq + source=java + 文件 OSS 地址（文本消息额外带内容签名 _sign），然后通过生产者适配器发送。适配器会根据配置自动选择 RocketMQ 5.0 gRPC 还是 Redis Streams，下游对此无感。

类：MessageProducerAdapter / RedisMqProducer / HouyiTcpConstructionMessageProduct　Key：msgId
9

推进书签，进入下一轮

只有整批消息处理成功，才把最新的 seq 写回 Redis。所以服务崩溃、重启都不会丢消息，最多是重复处理一次，而重复数据会被 MD5 索引和消息已存在判断挡掉。

方法：Message.setLastSeq()　特殊逻辑：corpId 为 ww0aad5bd009edd8e0 时按 10 条一批并发处理
04

重点展开：媒体文件的处理链路

消息里最常见的其实是图片、语音和小文件。它们不占消息体，只有一个文件 ID，必须二次下载。这条链路也是整个系统最容易失败、最需要重试的地方。

失败怎么办：下载失败、MD5 不通过、OSS 上传失败时，系统会把整条消息连同「已重试次数 tryCount」封装成延迟消息， 投递到重试队列（Redis 用 ZSet 记录到期时间，每秒扫描；RocketMQ 用延迟消息 + 重试消费者轮询）。 到期后重新提交到下载线程池；如果消息此时已经成功下载过，则直接确认丢弃。超过最大重试次数才真正放弃并记录错误。
05

后台定时任务：保证长期稳定运行

除了实时拉取，还有一批清扫和补偿任务，避免数据越积越多或漏推。

触发时间任务作用
每 1 秒延迟消息扫描扫描 Redis 延迟队列，把到期的重试消息投递到重试 Stream。
每天 02:00延迟队列清理清理已完成、过期的延迟消息，防止 ZSet 无限膨胀。
每天 03:00Redis 备份清理清理消息备份数据。
每天 04:00–08:59 每分钟历史消息删除删除已处理完成的历史消息记录，控制数据库体积。
每 10 分钟未推送消息重推扫描「处理成功但没推送成功」的消息，重新推送一次，保证下游不漏数据。
每 24 小时企业配置同步重新读取企业名单并同步到数据库，新增/停用企业无需重启。
06

对外暴露的接口

这个服务没有页面，只有几个运维接口。根路径 / 没有映射，访问会 404，属于正常现象。

接口用途说明
GET /status健康检查返回 200 即代表服务存活。
GET /api/open/status拉取状态按企业返回拉取成功 / 失败列表，例如 {"succ":[],"fail":[]}。
GET /api/open/pull/corp?corpId=补充企业从上游接口拉取企业的名称、密钥并入库（新部署时用）。
GET /api/open/trigger/corp?corpId=手动触发为某个企业立即启动拉取线程，不必等重启。
GET /api/open/single/msg?corpId=&msgId=&seq=单条补拉对某条历史消息重新执行下载与推送。
07

技术栈与运行方式

技术上它是什么

一个 Spring Boot 3.2 单体应用，单 jar 部署，用 Supervisor 守护。核心是「线程 + 线程池 + 定时任务」，不依赖微服务框架。

Java 21Spring Boot 3.2.11Spring Data JPA 企业微信 Finance SDKJedis / Spring Data Redis RocketMQ 5 gRPC阿里云 OSS SDKMicrometer

本地为什么只能“空跑”

本地用 H2 文件库替代 MySQL、Redis 用独立 db，企业配置置为停用。因为企业微信 SDK 只提供 Linux/Windows 的动态库，macOS 无法真正拉取消息，所以本地只验证服务启动与接口，不会产生真实数据。

H2 文件库本机 Redis db5企业全部停用端口 18080
